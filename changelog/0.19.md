# What's new in FactorIA 0.19

The 0.19 releases, newest first. The newest version is in [CHANGELOG.md](../CHANGELOG.md).

## 0.19.0

FactorIA 0.19.0 (M70) puts the engine's work on threads and loads games faster. A job system runs the big pieces of a
frame (sprites, tilemaps, particles, 3D culling, animation, physics, path searches, sound rendering) on worker threads,
set by `runtime.jobThreads`, and `game.state_hash` shows a game computes the same with any thread count. Scenes and
assets load in the background (`scene.load {async: true}`, `scene.preload`, `assets.preload`) while frames keep
running, with GPU uploads budgeted per frame. `game.pak` is memory-mapped, compressed per block with the engine's own
LZ4 and Zstandard, and packed in the order the game reads its files; `play.report` says how long each load took. The
player shows its first frame before reading the game, D3D11 keeps compiled shaders on disk, and `perf.startup` budgets
the start-up time.

### Changes

- **For game authors and AIs:** `factoria export` warns when a shipped script calls a project command with a literal name (`fa.call("project.scatter_gems", ...)`) that a tool module under `tools/` (subfolders included) defines: `tools/` is left out of the game, so in the shipped game that call fails. The warning names the script, the command and its tool file, and says to move the shared code into a module under `scripts/`.
- **For game authors and AIs (M70.2a):** the drawing work of a big frame runs on the job threads: the sprites (512 and more, 128 per job), tilemaps with 16384 or more visible cells (bands of rows), particles from 2048 live ones (their simulation and their quads, whole emitters per job), the 3D meshes from 256 (matrices, bounds and frustum culling, shadow bounds and casters), the sorts and the vertex stream, and the poses of animators with 512 or more skeleton nodes to pose. Below those counts, and with `jobThreads` 0 or `"inline"`, everything stays on the main thread as before; sokol_gfx calls never leave it. The frame is byte-identical with any thread count (NaN sort keys included: a NaN position, distance or colour sorts as +infinity), and from one run to the next: the 3D batches are now ordered by asset names instead of memory addresses, so coplanar opaque meshes of different materials draw the same in every run (engine/render/tests/render_jobs_tests.cpp, the ctest `example_jobs_same_frames`); `perf.profile`'s `threads` shows the jobs (`render.gather_sprites`, `render.particles`, `render.mesh_cull`, `scene.animation_poses`...). Small differences: an `autoDestroy` emitter that finished is now destroyed after every emitter of the frame has stepped, so a child emitter of it still steps in that frame (it is not drawn: the destroy hides the child at once, as before), and an emitter whose sub-emitter links to it with `{"entity": id}` may still copy its settings in that frame. docs/ARCHITECTURE.md, "Systems that run as jobs"; docs/PERFORMANCE.md, "Job threads".
- **For game authors and AIs:** `game.pak` (a `--release` export) is format 2: every file in checksummed 256 KiB blocks, each compressed with the codec of its type (`store` for PNG, OGG, MP4, supercompressed KTX2 and other compressed data; `zstd` for fonts and text; `lz4` for JSON, scenes, scripts, meshes and the rest). `export.pack.codecs` in `factoria.json` picks another codec per extension (`{".json": "zstd"}`). A damaged or cut-short pack is an error that names the file and block. Packs of FactorIA 0.18 (format 1) are still read.
- **For game authors and AIs:** play sessions (the editor's Play, `factoria run`, `play.auto`) record which files the start-up and each scene read first into `.factoria/cache/load-order.json` (under the project's lock; an exported game records nothing), and the export writes `game.pak` in that order, start-up files and main scene first, so a load reads the drive mostly forward. A `factoria run` or `play.auto` sets a scene's order; an editor Play, whose files are mostly cached already, only adds what was missing. `export.pack.useLoadOrder: false` packs by path. The export prints the pack's size per codec, the ratio and whether the order was used (`packStats` in the JSON report).
- **For game authors and AIs:** `play.report` has a `loading` section: time to the first frame, each scene's load time, files and bytes, the slowest assets split into read and decode time, and how many reads came from the pack. The times are rounded and are this machine's: compare runs, never pass or fail on them.
- **For engine code:** the player memory-maps `game.pak` on 64-bit desktops (positional reads on 32-bit, the web and with `FA_PACK_MAP=0`), and `fa::fs::read_view` returns an `fs::FileView` that points into the mapping, a warm file or an Android APK buffer without copying when it can (the background loader of M70.3 will use it). On Windows, an export over a game that is running from its folder stops before it deletes anything with `export: '<file>' is open in another program (the game running from <folder>?): close it and export again`, and the previous export stays (`fs::find_file_in_use`, which looks at the exe, the libraries and the pack; a pack read without mapping does not stop it, as Windows deletes that one); an Android export deletes the APK and AAB outputs of the previous build before Gradle runs, so a build that writes nothing is reported as such; an export over an Android export keeps Gradle's working folders (`.gradle/`, `build/`, `app/build/`...), which the Gradle daemon holds open, so two Android exports in a row work on Windows and the second build is incremental; a read-only file of an earlier export no longer stops the delete. A `fa::LoadTrace` belongs to its engine through a token that is never reused (`LoadTrace::new_owner`, `LoadTrace::ReadingFor`), not to a thread, and the engine's frames, draws and scene loads read for it however they are called. A pack entry over 64 times the pack's size (at least 256 MiB) is refused as damaged.
- **For engine developers (M70.4a):** the engine's own LZ4 and Zstandard codecs behind `fa/core/compress.h` (no outside library). `Codec::Lz4` reads and writes the LZ4 block format (levels 1 to 12: a fast greedy level 1-2, a hash chain with lazy matching from 3); `Codec::Zstd` reads every Zstandard frame the reference tool writes (all levels including `--ultra`, `--long` windows up to 128 MiB, Huffman and FSE tables of every kind, repeat offsets, skippable and concatenated frames, the content checksum; a dictionary or a larger window is an error that says so) and writes valid frames with the content size, Huffman-coded literals and FSE-coded sequences (levels 1 to 19; level 3 makes a smaller frame than `zstd -3` on the files tried). Output is deterministic on every platform. Decoders check every bound and refuse an `expectedSize` the block cannot hold before allocating. docs/ARCHITECTURE.md, "Block codecs".
- **For game authors and AIs (M70.1):** `runtime.jobThreads` in factoria.json sets the worker threads of the engine's job system: `"auto"` (the default: hardware threads - 1, at most 8 on desktop and 4 on phones; 0 in a web build), a number 0..32 written as a whole number (0 runs every job on the main thread; `"4"` in quotes and `4.0` are refused with a hint), or `"inline"` (debugging: every job runs at once on the thread that submits it). The `FA_JOB_THREADS` environment variable overrides it for one run (a bad value is reported and the file's setting is used); a bad value in the file stops the start with an error at `/runtime/jobThreads` and a "did you mean" (the words are exact there: `"Inline"` is refused with the spelling to use). `jobs.info` says what runs: workers, mode, the setting and where it came from, the jobs of the last frame, how busy each thread was, the threads waiting now and this engine's unfinished jobs (`enginePending`). `game.state_hash {perEntity?, includeRuntime?, maxEntities?}` returns one 64-bit hash of every entity, component and field, the clock and the random generator: the same at the same frame with any thread setting and in a replay (`perEntity` finds the entity that differs). The profile of `perf.profile` and `play.report` has a `threads` section (one entry per thread: job time, share of the frame, its slowest jobs by name), and the editor's Profiler panel a **Threads** tab with one row per thread (editor autotest section A2). See docs/PERFORMANCE.md, "Job threads".
- **For game authors and AIs (M70.2b):** a big game now uses the job threads for physics, path searches and sound rendering, with the same result as without them (`game.state_hash` is identical with `jobThreads` `inline`, 1, 2 or 8). A 2D step with 1536 or more awake bodies or 4096 or more contacts, a 3D scene of about 128 bodies or more, `render_sfx` of a patch with 2 or more layers and half a second or more of sound: they split over the workers; smaller ones run as before on the main thread, so a small game costs the same. Worlds this big (a 2D step with 1536 or more awake bodies or 4096 or more contacts) may settle differently than in 0.18: Box2D's choice of which island to split next, when several have the same sleep time, now follows the same four pieces whatever the thread setting, and that is not the order the single-threaded engine used, so recordings made in 0.18 of such worlds may not replay identically (smaller worlds are unchanged). New: `nav.find_paths {queries, radius?, snap?, closest?, mesh?}` / `nav.findPaths(queries, opts)` and `nav.find_tile_paths {map, queries}` / `nav.findTilePaths(map, queries, opts)` answer many path queries in one call, in the order asked, as fast as the job threads allow with 8 or more queries (at most 10000); one wrong query fails the call with its number and JSON pointer before any search runs. docs/NAVIGATION.md, "Many paths at once"; docs/PERFORMANCE.md, "Physics on jobs".
- **For engine developers (M70.2b):** Box2D's task system runs on `fa::jobs` (`B2JobTasks`, `physics2d_tasks.cpp`; the world's worker count is the constant 4 and a wide step cuts every task into the same at most 4 pieces from the item counts alone: with a stopped pool, inline mode, no workers or off the main thread the pieces run one after the other on the calling thread, so the result never depends on the pool); the 3D rigid-contact manifold pass and the contact-event pass scan rows as `parallel_for` and replay their slots in `(chunk, row, k)` order; `NavGrid::Scratch` lets searches run at once on one grid (`Physics::nav_find_paths`, `nav_tile_run_many`); `render_sfx` renders layers as jobs and sums them in layer order (noise streams keyed by seed, layer and oscillator). Tests: `engine/physics/tests/test_physics_jobs.cpp` (2D and 3D scenes hashed with inline/1/2/8 threads, small scenes queue no job), batch cases in `test_nav.cpp` and `test_nav_tiles.cpp`, `test_sfx.cpp` (layered patch identical in every mode), and `jobs_engine_tests.cpp` (a physics scene of hundreds of frames, hash every 10th frame, in every mode). Rules and merge orders: docs/ARCHITECTURE.md, "Physics, navigation and audio on jobs".
- **For engine developers (M70.1):** `fa/core/jobs.h`: `jobs::start`/`stop` (reference counted; the Engine calls them; `start` returns a `Result` and refuses another thread and calls from inside a job), `jobs::Owner` and `OwnerScope` (each Engine owns the jobs and main-thread tasks queued in its init, frames, scene loads and commands: shutdown waits for its own jobs, a frame runs only its own tasks, `end_frame(owner)` lets one engine close the job statistics; `CommandRegistry::set_job_owner`), `submit(name, fn, deps)` with `Handle`, `wait`, `wait_all` and `Group`, `parallel_for` with deterministic chunks (`Chunk::rng()` from a seed and the chunk index), `parallel_map_chunks` and `parallel_reduce` that merge in chunk order, `post_main` / `run_main_thread_tasks` for results that go back to the main thread, `info()`/`info_json`, settings parsing (`parse_settings`, `parse_settings_text`, `auto_worker_count`). A wait runs only what the job it waits for needs (never an unrelated job; `parallel_for` runs only its own chunks and `Owner::wait` only what its owner needs), so it ends with 0 workers too; `parallel_for` never returns while one of its chunks runs on another thread; a wait that can never end (through any chain of waits) returns an error instead of hanging, a job that throws is caught and fails the jobs that depend on it. `fa/scene/state_hash.h` (`world_state_hash`, `entity_state_hash`, `state_hash_hex`; components go in sorted by type name, not registration order), `EngineConfig::jobThreads`, `ProjectSettings::jobThreads`, `Profiler::add_job` and `ProfFrame::lanes`. The rules a job follows to stay deterministic, and the one for log sinks (thread-safe: they run on the thread that logs), are in docs/ARCHITECTURE.md, "Jobs and threads".
- **For game authors and AIs (M70.5):** the player shows its first frame (black, the letterbox colour) as soon as its window exists, before any game file is read; the game is read in the next frame and the GPU pipelines the first scene draws with are made over the frames after it (as many per frame as fit in about 8 ms), so a slow start is no longer an invisible window. It applies to the player and to a windowed `factoria run`, is always on, and changes nothing the game computes (`state_hash`, recordings, replays and goldens are identical). `play.report` `loading.startup` and the headless report's `startup` give `firstPresentMs` (the first frame shown; `null` with no window) and `firstGameFrameMs` (the game playable) apart, and a windowed run logs one `startup:` line.
- **For game authors and AIs (M70.5):** `perf.measure` and `perf.baseline` report `startupMs` (CPU milliseconds from reading the game's files to its first frame); `perf.check` compares it with the baseline (tolerances `startup`, ratio 2.0, and `startupSlackMs`, 500) and with the new absolute cap `budgets.maxStartupMs` (`perf.startup`). The three templates ship `perf.json` with `"maxStartupMs": 5000`. A time over its limit fails only when `CI` is set, and the message says how to bring start-up down.
- **For engine developers (M70.5):** a shader cache on disk for Direct3D 11: the engine compiles each stage once with `d3dcompiler_47`, keeps the bytecode in the per-user cache folder (`fs::cache_dir()`; `FA_CACHE_DIR` overrides; the game folder never holds it) and hands it to sokol next time. Note that `sokol-shdc` writes shader source, not bytecode, and sokol accepts compiled programs only on D3D11: OpenGL, OpenGL ES and Metal keep relying on the driver's and the OS's own caches and the web has no disk cache (docs/PERFORMANCE.md, "Startup", has the per-backend table; `renderer.supports(...)` is planned, not in the engine yet). Cache files are named after a hash of their key, so two engine versions or two games never replace each other's entry, and `ctest` points `FA_CACHE_DIR` at a scratch folder of the build. `fa::fs::cache_dir()` returns a path by value and `reset_cache_dir()` forgets `set_cache_dir`. `fa/core/blob_cache.h` (`BlobCache`: magic, version, key, size and SHA-256 header, atomic store, a file with another key or a bad checksum is ignored with one log line and rebuilt), `fa/core/startup.h` (`StartupTimeline`), `fa/runtime/startup_sequence.h` (`StartupSequence`), `Renderer::present_clear` / `warm_step` / `startup_report`, `EngineConfig::adoptGraphicsContext`.

- **For game authors and AIs (M70.3):** background loading. `scene.load(path, props, { async: true })` (and the command `scene.load {"path", "async": true}`) loads a scene while frames keep running and switches to it at the end of the frame its files are ready, with the same world, props and first-use file order as a sync load; a newer scene load cancels it. `scene.preload` and `assets.preload` now read on an IO thread and decode textures (PNG, KTX2/Basis), models, fonts and sounds on worker threads; the main thread only uploads, within `runtime.loadBudgetMs` (default 4) and `runtime.uploadBudgetMB` (default 16) per frame in a game with a window, which never waits for a file. Tests, headless runs, the editor and replays take exactly 4 files per frame, so they see the same frames on every machine and with any `runtime.jobThreads`; a recording keeps how many files each frame of a windowed run took (`"loadUnits"`) and replays them. The handle has `total`, `uploadedBytes`, `cancelled` and `cancel()` besides `progress`, `done`, `files`, `bytes`, `error`, `promise` and `release()`; new commands `scene.preload`, `assets.preload`, `load.status` and `load.cancel`. A missing file is an error with "did you mean". The menu kit's loading screen (`scripts/loading.js`) loads the first level this way and shows the real progress. Nothing runs (no thread, no work) while no background load does (docs/PERFORMANCE.md, "Background loading").
- **For engine developers (M70.3):** `fa/core/background_io.h` (`IoQueue`: one process-wide IO thread serving each engine's queue in turn, reads through `fa::fs`, decodes as jobs of the engine's owner, `take()` that does an unstarted item itself), `LoadTrace::ReadingFor(owner, tag)` reads ahead, `LoadTrace::file_used`, `scene_requested`/`load_cancelled` and `FileCollector`, so an async load records the order of a sync one; `Renderer::background_kind`/`background_cached` and `background_work` and `adopt_background` for textures, models and fonts, `Audio::decode_clip`/`adopt_clip`; `EngineConfig::timedLoads`; `InputRecorder::load_units`. The script preload module moved from `fa_script` into the runtime's `BackgroundLoader`, which scripts reach through `ScriptHost::background_load_start`/`cancel`/`reset`; `ScriptHost::drop_script_background_loads` stops a script's loads when its JavaScript context is created or closed. The loaders of every engine count their references to warm files, so one engine never drops a file another read ahead. Font faces are cached by normalized path (`./fonts/a.ttf` and `fonts/a.ttf` are one face).
- **Fix (Windows):** a project in a folder whose name has an accent (any letter that is not ASCII) now
  writes its files there (the load order, saves through `fa::fs` with an absolute path): `fa::fs::resolve` read the
  UTF-8 path in the code page and wrote to a folder of another name. An export over a game that runs from its `game.pak`
  says the pack is open in another program on Windows too, where the replace answers "access denied".
